# 008 · 2026-11-13：任务拆解 + 执行反馈修正、真实试玩按钮、版本号

## 为什么做
比赛要求“拆解任务并调用工具，须展示至少一次基于执行反馈的修改”。走查发现：没有计划步骤；SYSTEM_PROMPT 写死“按顺序，每步只做一次”，等于禁止“看到失败再改”；已有三次真实修复运行的工具结果都是一次通过，修复指令还直接给了坐标。

## 做了什么
- 工作流改为：inspect → run_rule_checks（诊断）→ submit_plan → 补丁 → 复测 → 浏览器回放 → prepare_review；失败必须依据详情重改。
- `submit_plan`：2–6 步，`checkIds` 必须是真实检查 id；进度由后端 `planProgress()` 按检查结果判定，写入 `plan.json`。
- `feedback_fix`：后端识别“检查失败 → 补丁 → 同一检查通过”，计入 `run.feedbackFixes`；基线诊断失败不计入修复轮预算。
- `prepare_review` 拒绝计划中未通过/未检查的子任务。
- 时间线新增“AI 的任务拆解”和“基于执行反馈的修改”卡片。
- 验证面板“运行真实试玩”原来只重跑规则检查，部分验证永远过不去；新增不调用 AI 的 `POST /api/projects/:id/playtest`。
- 版本号：采纳时由创作者选小修改 +0.1 / 大修改 +1。
- `node scripts/test.mjs <suite> <文件名片段>` 支持只跑单个测试文件，避免真实模型测试一次全跑产生多余费用。

## 踩坑
- `plan.json` 最初只在提交计划时写一次，进度更新后文件仍是旧状态；改为每次复测/回放后重写。
- 浏览器回放后复验会把 reachable_goal 从 partial 变 passed，所以回放后也要刷新计划进度。
- e2e 在 CDP 模式下全部失败、无头模式全部通过：本机 9222 端口的浏览器会话被其他工具占用，属于环境问题。

## 真实模型盲修结果
通过：8 次请求、5730 tokens，基线失败 → 计划 → 补丁 → 复测通过 → 浏览器 18 步通关。模型把出口也挪了位置（指令没禁止），说明 scope_drift 在指令不点名对象时不会触发，后续可把“修改实体数超过失败检查涉及对象”作为新的可疑标记。
